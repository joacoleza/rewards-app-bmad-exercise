# Story 1.3: Backend Authentication API

Status: done

## Story

As a user,
I want to log in with my email and password and receive secure tokens,
So that I can access the application with my identity verified and session maintained.

## Implementation Summary

- `apps/api/src/app.ts` now builds the API with fail-fast env loading, structured Fastify/Pino logging, cookie support, CORS, centralized error handling, and `/api/auth` route registration.
- `apps/api/src/plugins/env.ts` validates `DATABASE_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`, `NODE_ENV`, `PORT`, `LOG_LEVEL`, and `CORS_ORIGIN`, and exposes typed `fastify.config` values to the app.
- `apps/api/src/services/authService.ts` delivers bcrypt password hashing/verification plus HS256 JWT access and refresh token generation/verification with the required 15-minute and 8-hour lifetimes.
- `apps/api/src/services/auditService.ts` writes structured audit log entries, and successful login now records `USER_LOGIN` events without leaking secrets.
- `apps/api/src/routes/auth/index.ts` implements `POST /api/auth/login`, `POST /api/auth/refresh`, and `POST /api/auth/logout` with JSON Schema validation, generic unauthorized messaging, httpOnly refresh cookies, and cookie clearing on invalid refresh/logout flows.
- The refresh response returns both a replacement access token and the resolved user payload, which the frontend now uses for session restoration.

## Validation Summary

- `apps/api/src/plugins/env.test.ts` verifies startup failure when required env vars are missing or invalid.
- `apps/api/src/server.test.ts` verifies the centralized error handler and production-safe internal error behavior.
- `apps/api/src/services/authService.test.ts` covers password hashing, JWT generation, expiry handling, wrong-secret rejection, and malformed payload rejection.
- `apps/api/src/services/auditService.test.ts` verifies audit insertion behavior and null payload normalization.
- `apps/api/src/routes/auth/index.test.ts` covers successful login, audit logging, invalid credentials, validation failures, refresh success/failure, deleted-user refresh rejection, and logout cookie clearing.

## Acceptance Criteria

1. **Given** a registered user with valid credentials, **When** I POST /api/auth/login with `{ "email": "...", "password": "..." }`, **Then** I receive a 200 response with an access token (JWT, 15-min expiry, contains sub + role), **And** a refresh token is set as an httpOnly cookie (8-hour expiry), **And** an audit log entry is created with action USER_LOGIN, actor_id set to the user, and entity_type USER (FR38).

2. **Given** an invalid email or wrong password, **When** I POST /api/auth/login, **Then** I receive a 401 response with `{ "error": "UNAUTHORIZED", "message": "Invalid email or password", "statusCode": 401 }`, **And** no token is issued, **And** the error message does not reveal whether the email exists.

3. **Given** the login request body is malformed (missing email or password), **When** I POST /api/auth/login, **Then** I receive a 400 response with the consistent JSON error shape including the `field` property, **And** the error is generated by Fastify JSON Schema validation.

4. **Given** a valid refresh token cookie, **When** I POST /api/auth/refresh, **Then** I receive a new access token with refreshed expiry, **And** the refresh token cookie is preserved.

5. **Given** an expired or invalid refresh token, **When** I POST /api/auth/refresh, **Then** I receive a 401 response, **And** the refresh token cookie is cleared.

6. **Given** an authenticated user, **When** I POST /api/auth/logout, **Then** the refresh token cookie is cleared server-side, **And** I receive a 200 response confirming logout.

7. **Given** the @fastify/env plugin is configured, **When** the API server starts without required env vars (JWT_SECRET, DATABASE_URL), **Then** the server fails to start with a clear error message listing missing variables.

8. **Given** the API server is running, **When** I inspect log output, **Then** Pino structured JSON logs are produced, **And** log level is configurable via LOG_LEVEL env var, **And** passwords are never logged.

## Original Dev Notes (Historical Reference)

### Authentication Architecture (MUST FOLLOW)

| Aspect | Specification |
|---|---|
| Access token algorithm | HS256 |
| Access token expiry | 15 minutes |
| Access token payload | `{ sub: userId, role: "employee" \| "manager", iat, exp }` |
| Access token delivery | Response body as `accessToken` field |
| Refresh token expiry | 8 hours (matches NFR8) |
| Refresh token payload | `{ sub: userId, iat, exp }` |
| Refresh token delivery | httpOnly cookie named `refreshToken` |
| Password hashing | bcryptjs, 12 rounds |
| Password storage | Never plaintext, never logged, never in API response |

### JWT Token Details

**Access token:**
```typescript
// Generate
const accessToken = jwt.sign(
  { sub: user.id, role: user.role },
  process.env.JWT_SECRET,
  { algorithm: 'HS256', expiresIn: '15m' }
);

// Verify
const decoded = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'] });
// decoded.sub = userId, decoded.role = 'employee' | 'manager'
```

**Refresh token:**
```typescript
// Generate
const refreshToken = jwt.sign(
  { sub: user.id },
  process.env.JWT_REFRESH_SECRET,
  { algorithm: 'HS256', expiresIn: '8h' }
);

// Set as httpOnly cookie
reply.setCookie('refreshToken', refreshToken, {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'strict',
  path: '/api/auth',
  maxAge: 8 * 60 * 60, // 8 hours in seconds
});
```

### Consistent Error Response Shape (CRITICAL)

All API errors MUST follow this format — established in this story, used by all future stories:

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Email is required",
  "field": "email",
  "statusCode": 400
}
```

**Error codes** (define in packages/shared/src/errors.ts):
- `VALIDATION_ERROR` — 400
- `UNAUTHORIZED` — 401
- `FORBIDDEN` — 403
- `NOT_FOUND` — 404
- `CONFLICT` — 409
- `DUPLICATE_NOMINATION` — 409
- `INTERNAL_ERROR` — 500

**Fastify setErrorHandler pattern:**
```typescript
fastify.setErrorHandler((error, request, reply) => {
  // Handle Fastify validation errors (from JSON Schema)
  if (error.validation) {
    const firstError = error.validation[0];
    return reply.status(400).send({
      error: 'VALIDATION_ERROR',
      message: error.message,
      field: firstError?.params?.missingProperty || firstError?.instancePath?.replace('/', '') || null,
      statusCode: 400,
    });
  }

  // Handle known application errors
  if (error.statusCode) {
    return reply.status(error.statusCode).send({
      error: error.code || 'INTERNAL_ERROR',
      message: error.message,
      field: error.field || null,
      statusCode: error.statusCode,
    });
  }

  // Unknown errors
  request.log.error(error);
  return reply.status(500).send({
    error: 'INTERNAL_ERROR',
    message: process.env.NODE_ENV === 'production' ? 'An unexpected error occurred' : error.message,
    field: null,
    statusCode: 500,
  });
});
```

```typescript
const loginSchema = {

            id: { type: 'number' },

            role: { type: 'string', enum: ['employee', 'manager'] },
          },
        },
      },
    },
  },
};
```

### Audit Logging Pattern (Transactional)

Login audit log must be created IN the same transaction as any state change. For login specifically, the audit log is independent (no state change to users table), but the pattern should be established for consistency:

```typescript
// In login handler
import { db } from '@bmad/db';
import { auditLogs } from '@bmad/db/schema';

// After successful password verification:
await db.insert(auditLogs).values({
  actorId: user.id,
  action: 'USER_LOGIN',
  entityType: 'USER',
  entityId: user.id,
  payload: { email: user.email },
});
```

For future stories with domain mutations (nomination create, approve/reject), the pattern MUST use `db.transaction()`.


### Anti-Patterns to AVOID

- Do NOT store tokens server-side — JWT is stateless (NFR16)
- Do NOT reveal whether an email exists in error messages — always "Invalid email or password"
- Do NOT log passwords, tokens, or secrets via Pino
- Do NOT use `any` type — use proper types from jsonwebtoken and bcryptjs
- Do NOT create RBAC middleware in this story — that is Story 1.4
- Do NOT add requireAuth/requireRole hooks — that is Story 1.4
- Do NOT protect any routes in this story — auth middleware comes in Story 1.4
- Do NOT implement @fastify/swagger in this story — just register a placeholder plugin if needed
- Do NOT use raw SQL — use Drizzle query builder for audit log inserts

- **Protected route enforcement** (Story 1.4)
- **Frontend login page** (Story 1.6)
